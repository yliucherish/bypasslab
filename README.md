# BypassLab

> 一个用 Go 写的**反向代理式 WAF**，配套本地靶场与对抗驱动脚本：用于研究「攻击 → 拦截 → 绕过 → 补规则」的完整对抗循环。
> 全部测试仅针对本地靶场与自建环境。

## 为什么做这个项目

写过扫描器（VulnHunter）、写过检测引擎（SentinelWatch）之后，缺的是**对抗层**：
同一个 payload，为什么有的 WAF 拦得住、有的拦不住？规则加严到什么程度开始误伤业务？
这些问题只能靠"自己造一个 WAF，再自己打它"来回答。

BypassLab 就是这个实验台：WAF 与攻击方都是自己的代码，因此每一轮绕过都能追溯到**具体哪条规则被什么变了形绕过**，
也能量化"补规则之后拦截率涨了多少、误报有没有变多"。

> **结论先行**：训练集能修到 100%，但冻结的 holdout 集只有 **63.2%**。
> 前者是拟合，后者才是规则型 WAF 的真实水位——详见 [Holdout 一节](#holdout一个不会说谎的数字632)。

## 架构

```
                    ┌──────────────── BypassLab ────────────────┐
client ──请求──▶    │  限流 → 归一化 → Layer1 正则 → Layer2 语义  │ ──放行──▶ upstream（靶场 echo）
                    │                    ↓ 命中                 │
                    │          403 + 规则ID + JSONL 审计日志      │
                    └───────────────────────────────────────────┘
                                              │
                                     logs/waf.jsonl
                                （可被 SentinelWatch 采集联动分析）
```

**双层检测**是核心设计：

| 层 | 作用 | 特点 |
|---|---|---|
| Layer 1 正则 | 16 条内置规则，覆盖 SQLi / XSS / RCE / 路径遍历 / 反序列化 / SSRF / 扫描器指纹 | 快、可解释、易被变形绕过 |
| Layer 2 语义 | 16 个特征加权求和，达到阈值才拦（默认 5 分，**按字段独立计分**） | 慢一点、抗编码与拆分变形、误报可控 |

归一化层在两层之前做八件事（每一件都对应一类绕过手法）：
多轮 URL 解码至不动点 → HTML 实体解码至不动点 → `\u003c` / `\x3c` 转义展开 →
`${lower:}` / `${upper:}` 展开 → 去 SQL 注释 → 压缩空白 → 折叠斜杠 → IP 字面量归一（十进制 / 十六进制 / 八进制 / 简写）。

## 快速开始

需要 Go 1.22+，无第三方依赖。

```bash
# 终端 1：启动本地靶场（无任何过滤，仅用于授权测试）
go run ./cmd/echo -listen :9000

# 终端 2：启动 WAF，保护靶场
go run ./cmd/waf -listen :8080 -upstream http://127.0.0.1:9000 -log logs/waf.jsonl -rate 120

# 终端 3：跑基线验收（15 个用例：3 个正常 + 12 个攻击）
bash scripts/demo_w1.sh
```

正常请求：

```bash
curl -i "http://127.0.0.1:8080/api/orders?page=2&size=20"
# HTTP/1.1 200 OK  ← 转发到靶场
```

攻击请求：

```bash
curl -i "http://127.0.0.1:8080/product?id=1%20UNION%20SELECT%20password%20FROM%20users"
# HTTP/1.1 403 Forbidden
# X-BypassLab-Blocked: BL-SQLI-001
# {"blocked":true,"rule_id":"BL-SQLI-001","category":"sqli","severity":"high","layer":"regex"}
```

内部端点：`/__waf/health`（规则数、启动时长、放行数、语义阈值）、`/__waf/stats`（按规则统计拦截数、allow/block 计数）。

### W2 对抗驱动器

把内置语料库（112 条：84 攻击 + 28 良性对照）批量打向 WAF，输出结果矩阵与报告：

```bash
# 一键复现（自己起靶场与 WAF，跑完自动清理）
bash scripts/run_w2.sh

# 或手动指定目标
go run ./cmd/attack -target http://127.0.0.1:8080 -csv out/w2_matrix.csv -md out/w2_report.md
```

产物：`out/w2_matrix.csv`（逐条明细：状态码 / 是否拦截 / 命中规则 / 命中层 / 耗时）、
`out/w2_report.md`（分类拦截率、规则分布、绕过清单、误报清单）。

单元测试：`go test ./...` **53 个测试函数全绿**（v1.4；CI 以 `go test -race` 运行，
覆盖归一化 22 组、规则逐条、语义层、误报面、规则数漂移、命中部位归因、代理端到端、

其中两个缺陷是跑基线时发现的，记录在此以免重犯：
1. **双计数导致假阳性归因**：早期把 `RequestURI` 计入 path 字段，导致 query 里的攻击被同时算作 path 命中，
   语义分被放大。修正后 query 攻击正确归因为 `query`。
2. **单字段恒真式漏报**：`?id=1' or 1=1` 仅积 4 分（阈值 5）→ 漏拦。修法不是降阈值（会误伤），
   而是把恒真式权重提到 4，叠加 comment 特征即达 5；单纯出现 `'or'` 仍不拦。

### 历史基线（v1.0，保留作对比）

同一批语义在 v1.0 规则下只有 **79.8%（67/84）**、误报 0（0/24）。
这 20 个百分点的差距**不是靠加规则凑出来的**，全部来自 [v1.1 审计](#v11-审计修复2026-10-26)
补掉的归一化缺口——原始矩阵固化在 `out/w2_matrix_v1.0.csv`，可逐条 diff。

### W2 当时暴露的 4 个真问题（W3 已全部修复）

1. **SSRF 几乎不设防**：`127.0.0.1`、`169.254.169.254`、`gopher://` 等 7 条全部放行。
   根因是语义层 `ssrf:internal-ip` 权重只有 2，单特征永远到不了阈值 5——**单一强特征也该能独立定罪**。
   → 已补 BL-SSRF-001 正则兜底。
2. **单竖线命令拼接漏检**：规则只覆盖 `;`、`&&`、`||`，漏了 `|`。→ 已补进 BL-RCE-001。
3. **`'1'='1'` 型恒真式漏检**：`isTautology` 只匹配「数字=数字」与 `'or'='or`，没覆盖引号包裹的数字。
   → 已补 `reQuotedPair`，并在 v1.1 放开了「末尾引号可省略」（`1' OR '1'='1` 这种经典 payload 才能命中）。
4. **JNDI 混淆变形**：`${${lower:j}ndi:...}` 未在归一化层展开。→ 已补 `${lower:}` / `${upper:}` 循环展开。

误报为 0 说明**当前阈值没有过紧**，W3 有加权的空间。

| 轮次 | 语料 | 本轮改动 | 拦截率 | 误报率 |
|---|---|---|---|---|
| R1 | 108 条（v1.0 规则） | —（W1 规则原样） | 79.8%（67/84） | 0%（0/24） |
| R2 | 112 条（v1.1） | 审计修复：解码到不动点、IP 字面量归一、按字段独立计分、误报面收窄 | **100%（84/84）** | 0%（0/28） |
| R3 | 130 条（v1.1 + 18 条更难变形） | 规则未改，只换语料 | 94.1%（96/102） | 0%（0/28） |
| R3′ | 130 条（v1.2 补 6 条） | 注释双版本、MySQL 版本注释、括号恒真式、IPv6 映射、`${env:}`、`%c0%af` | **100%（102/102）** | 0%（0/28） |
| R4 | 124 条（v1.2 + **12 条全新构造**） | 不参考任何缺口清单，按「同一语义还能怎么换写法」重新出题 | 97.9%（94/96） | 0%（0/28） |
| R4′ | 124 条（v1.3 补 2 条） | 版本注释拆关键字、八进制单段 IP | **100%（96/96）** | 0%（0/28） |

### 这张表最值得讲的一点

**每次修到 100%，就再出一批新题，然后又掉下来。**

- R3 修完 → 以为收敛了 → 独立构造 12 条全新语料（R4，不参考任何缺口清单）→ **掉到 97.9%**，
  暴露 2 条从没见过的绕过 → 修完 → 又回到 100%。

所以这张表里**唯一能代表泛化能力的数字是 R1 的 79.8%**——它是在"没有针对任何缺口做过修复"的
状态下测出来的。后面所有 100% 都只对"那一批语料"成立，**不代表任何真实防护水平**。

任何只报 100% 的 WAF 评测，都值得问一句「换一批 payload 还是 100% 吗」——包括我们自己。

### R4 又抓到什么（v1.3 已修）

| 样本 | 根因 |
|---|---|
| `/*!50000un*/ion select` | 版本注释展开时前后补了空格，把 `un` 与 `ion` 断开 |
| `http://017700000001:6379/` | 单段 IP 归一只认十进制与 `0x`，漏了前导 0 的八进制写法 |

这两条都不在 R3 的 6 条缺口清单里——**它们是被"重新出题"逼出来的，不是被"照着清单改"改出来的**。

### R2 修的两处实现缺陷（比加规则更关键）

1. **归一化的斜杠折叠把 `http://` 折成了 `http:/`** —— 这是 SSRF 规则完全失效的真因，
   加规则之前如果不看归一化输出，会一直以为「规则写了为什么不生效」。
2. **引号包裹的恒真式（`'1'='1'`）权重不足**：数字恒真式给 4 分，引号形态需要单独计分才能过阈值。

### R3 暴露的 6 条（v1.2 已全部修复）

| 类型 | 样本 | 根因 | 修法 |
|---|---|---|---|
| 归一化层缺一步 | IPv6 映射回环 `[::ffff:127.0.0.1]` | 只归一了 IPv4 的各种写法 | URL host 走 `net.ParseIP().To4()` |
| 归一化层缺一步 | `..%c0%af`（超长 UTF-8 斜杠） | 未处理 IIS 畸形 UTF-8 编码 | 解码前按字面替换 `%c0%af`/`%c0%ae` |
| 规则层缺一步 | `/*!50000union*/ select` | 版本注释剥离时把内容一起丢了 | 先展开 `/*!数字…*/` 再剥普通注释 |
| 规则层缺一步 | `un/**/ion se/**/lect` | 注释被替换成空格，关键字被拆成两段 | 同一字段同时匹配「保空格版」与「删注释版」 |
| 规则层缺一步 | `and (1)=(1)` | 恒真式不认括号包裹 | 新增 `sql:paren-tautology`（权重 5） |
| 规则层缺一步 | `${${env:FOO:-j}ndi:...}` | JNDI 只展开了 lower/upper | 展开 `${env:X:-y}` 取默认值 |

> v1.0 时期这张表有 9 条，v1.1 修掉了十进制 / 十六进制 / 八进制 / 简写 IP、`\u003c` 转义与 4 层 URL 编码，
> v1.2 修掉了剩下 6 条。**修完这张表之后我们造了 R4 的新语料，又掉下来 2 条**——见上表。

**共性结论**：能挡住「已知写法」，挡不住「同一语义的另一种写法」。规则层的天花板就在这里——
这也解释了为什么工业界会走到语义/语法分析（AST）与行为检测。

## 流式 body 检测（大文件上传可用）

之前的规则是：body 超过 `MaxBody` 直接 413。安全上干净，但**正常的大文件上传也会被挡掉**——真实站点没法用。

v1.6 改为两级：

| body 大小 | 处理方式 | 拦截能力 |
|---|---|---|
| ≤ MaxBody（默认 1 MiB） | 全量读取 + 精确检测 | 命中回 **403** |
| > MaxBody 或 chunked | **流式分块检测**（64KB 块 + 8KB 重叠窗口），原样转发 | 命中断开连接（502）+ 审计，内存占用恒定 |

流式的代价是明确的：响应可能已经开始，无法回 403——只能断连。这是所有流式 WAF 的共同取舍，
ModSecurity 也一样。关键设计：**重叠窗口**让横跨块边界的 payload 依然能被抓到（有专门测试覆盖）。

实测：

| 场景 | 结果 |
|---|---|
| 2 MiB 干净文件上传 | **200**，上游完整收到 2 MiB |
| 2 MiB 中间藏 `UNION SELECT` | 断开连接，审计记录 stream 层命中 |
| payload 横跨 32 KiB 块边界 | 被重叠窗口抓到 |
| chunked 传输（无 Content-Length） | 走流式检测，攻击被拦 |
| 谎报 Content-Length（声明 8 实发 64） | Go 标准库按声明截断，多余字节到不了上游 |

## 规则热加载（可运营性的最低要求）

真实场景里规则是天天要改的，改一次重启一次不现实。现在支持外部配置 + 热加载：

```bash
# 导出当前内置规则作为配置模板
./bin/waf -dump-rules rules/waf_rules.json

# 从外部 JSON 加载（同时开启热加载）
./bin/waf -rules rules/waf_rules.json -upstream http://127.0.0.1:9000
```

改完文件约 2 秒生效（轮询 mtime；不用 fsnotify 是为了守住零第三方依赖）。实测：

| 操作 | 结果 |
|---|---|
| 初始加载 16 条规则 | `?id=1 union select 1` → **403** |
| 从 JSON 里删掉 `BL-SQLI-001` | 4 秒后同一请求 → **200**，`/__waf/health` 显示 rules=15，**服务未重启** |
| 写入非法规则（空 ID / 坏正则 / 重复 ID / 非法 target） | **整体拒绝并保留旧规则**，WAF 不会变透明 |

最后一条是重点：热加载最危险的不是"加载不上"，而是"加载了半套然后裸奔"。
所以 `LoadRuleSet` 做全量校验（正则可编译、target / severity / action 合法、ID 唯一），
任何一条不过就整体拒绝，只打日志不动线上规则。

## 性能（单核实测）

`go test -bench . -benchmem ./internal/waf`，AMD Ryzen 7 6800H：

| 场景 | 耗时 | 折算单核 QPS |
|---|---|---|
| 归一化单次 | 6.0 µs | ~166k |
| 攻击请求检测（第一层即命中） | 11.1 µs | ~90k |
| 良性请求完整检测（16 正则 + 16 语义 × 5 部位） | 57.2 µs | ~17.5k |
| **端到端**（限流 + 检测 + 审计 + 转发） | **174 µs** | **~5.7k** |

瓶颈很明确：良性请求必须走完 16 条正则 × 4 个部位 + 16 项语义特征，而归一化还要对每个字段做多轮解码。

已做的优化：无块注释时只算一版归一化（砍掉一半开销）；同一请求内字段归一化结果缓存。

**没做的优化**（写下来免得被问住）：把 `ToLower` 提到字段级只做一次、正则合并成单次多模式匹配。
按当前定位，5.7k QPS 保护一个小站够用；再往下就是追 nginx 的尾灯，不如把时间花在规则上。

## Holdout：一个不会说谎的数字（63.2%）

上面所有 100% 都有一个共同前提——**语料参与了调参**。修完 R1 修 R2、修完 R3 修 R4，
每一批最终都会被修到 100%。它们是训练集，不是测试集。

所以单独留了一批**冻结语料**（`internal/payloads/holdout.go`，19 条），并配了三条硬纪律：

1. **不进任何主流程**：只由 `scripts/run_holdout.sh` 单独跑，CI 与 `run_w2/run_w4` 都不含它；
2. **只报总数，不报明细**：输出里连哪几条漏了都不打印——不知道是哪条，就没法针对性修；
3. 文件头写死：**任何情况下不得据此修改规则**。规则改动后重跑，数字下降是正常的。

结果：

| 语料 | 条数 | 拦截率 | 性质 |
|---|---|---|---|
| 训练集（R2 / R3 / R4） | 112 / 130 / 124 | **100%** | 参与过调参，**不能代表泛化能力** |
| **holdout（冻结）** | **19** | **63.2%（12/19）** | 从未做过针对性修复 |

**这 37 个百分点的差距，才是这个项目真正的结论**：规则型 WAF 对「同一语义的另一种写法」的
真实拦截率在六成上下，而不是 100%。任何只报 100% 的评测，几乎一定是在测试集上调过参。

> 为什么这个数字不修？因为一修它就变成训练集了。它的价值恰恰在于**一直难看**。
> 如果哪天规则真的泛化了，它会自己涨上去——那才叫进步。

## CRS 基准：39.0%——第三方给的分数

holdout 虽然冻结，但它仍是我自己造的。真正的第三方基准是 **OWASP CRS 官方回归测试集**
（github.com/coreruleset/coreruleset，tests/regression/ 目录）。我把其中四个规则文件
（942100 SQLi / 941100 XSS / 930100 LFI / 932130 RCE）逐条转写成我们的语料格式（`-crs` 运行）：

| 语料 | 条数 | 拦截率 | 误报 |
|---|---|---|---|
| 自造训练集（R4） | 124 | 100% | 0% |
| 冻结 holdout | 19 | 63.2% | 0% |
| **CRS 官方测试集** | **59** | **39.0%（23/59）** | 1/8* |

*那 1 条"误报"是口径差异：CRS 的 libinjection 不检查 Referer 头，我们检查——payload 放在
Referer 里 CRS 放行、我们拦截。这不是缺陷，是我们比 CRS 激进的代价（已计入，不掩饰）。

### CRS 暴露了什么（以及为什么不修）

CRS 测试集集中暴露了几类我们**完全没有的能力**，每类都不是"加一条正则"能解决的：

| 缺口类别 | 样本数 | 为什么难 |
|---|---|---|
| bracket globbing（`/etc/pa[s]wd`） | ~10 | 需要 shell 通配符展开语义，正则难覆盖所有组合 |
| IIS `%uXXXX` best-fit 编码 | 3 | IIS 专属解析行为，要先识别再折叠 |
| XML 载体（属性注入） | 3 | 需要 XML 解析器，否则看不到属性值 |
| 自定义标签（`<x:script>`） | 2 | 需要理解命名空间 |
| CRS 自家特征串（`0x5c0x2e.%00/`） | 2 | CRS 针对自己规则设计的特征，对别的 WAF 无意义 |

**这正是这个实验台的完整意义**：它不仅量化了"我对自己的语料 100%"，
还量化了"我对工业界标准测试集 39%"。两个数字放在一起，才是规则型 WAF 的真实能力边界。
CRS 社区用十几年积累了上千条规则才覆盖这些场景——
**这 61% 的差距就是工业界规则的护城河，也是这个项目诚实的边界**。

### 与 SentinelWatch 的联动接口

BypassLab 的拦截日志与 SentinelWatch 的采集协议字段对齐，因此不需要额外改造：

| BypassLab 字段 | 含义 | SentinelWatch 侧用途 |
|---|---|---|
| `event_type` | `waf_block` / `waf_allow` | 事件分类依据 |
| `src_ip` | 客户端 IP（支持 X-Forwarded-For） | 关联暴力破解 / 扫描行为 |
| `rule_id` / `category` / `severity` | 命中规则与危害等级 | 告警去重与分级 |
| `target` | 命中部位（path/query/body/ua/headers） | 判断攻击面 |
| `excerpt` | 命中片段（截断 120 字符） | 人工复核 |
| `ts` | UTC 时间戳 | 时间窗口聚合 |

联动方式（两条，任选）：

1. **文件管道**：`logs/waf.jsonl` 直接作为 SentinelWatch 的日志源（其 FIM/日志采集器按行读取 JSON）
2. **实时转发**：把 `-log` 指向命名管道，或让 SentinelWatch 侧 tail 该文件

> 状态：字段契约已实现并写入 W1；真正的双系统联调需要 SentinelWatch 仓库一起跑（本机暂无该仓库），
> 待仓库可访问后补一张「WAF 拦截 → 看板告警」的联动截图。

## v1.1 审计修复（2026-10-26）

对 W1–W4 全量源码做了一次逐行审计（报告见 [`AUDIT.md`](AUDIT.md)），共记录 18 项缺陷、
3 处文档漂移。本次修复了其中的必修项与大部分建议项，**数据全部重跑，旧数字不做保留**。

### 修掉的实现缺陷（这些问题比"少一条规则"严重得多）

| 类别 | 问题 | 修法 |
|---|---|---|
| **高危** | body 超过 `MaxBody` 被**静默截断后继续转发**，1 MiB 之后的载荷完全不检测 | 改为读 `limit+1` 字节判定，超限直接 **413 + `BL-OVERSIZE`**，不转发 |
| **高危** | `/__waf/health` 无锁读 `passages`，与写侧构成 **data race** | 读侧补 `RLock`；CI 改为 `go test -race` 并新增并发测试 |
| 中 | 限流无条件信任 `X-Forwarded-For`，伪造头部即绕过 | 新增 `-trusted-proxies`，默认不采信 XFF |
| 中 | 限流器 `hits` map 从不回收空闲 IP，内存无界增长 | 加惰性清理（阈值 + 最小间隔） |
| 中 | HTML 实体只解 1 轮，`&amp;lt;script&amp;gt;` 绕过 XSS 全部规则 | 解到不动点（上限 3 轮） |
| 中 | URL 解码硬上限 3 轮，4 层编码绕过 | 解到不动点（上限 8 轮） |
| 中 | 语义分**跨字段累加**，query 4 分 + body 无关 1 分即拦截 | 改为**按字段独立计分**，归因精确到字段 |
| 中 | 裸 `' or '` 被 tautology(4) + comment(1) 双重计分，正常文本误报 | comment 特征不再包含裸 `' or '`，恒真式必须由等式判断 |
| 中 | `javascript:` / 扫描器关键词作用于 body，技术文档被误伤 | 两类规则收窄到 path/query/headers 与 UA/headers |
| 中 | 报告器 `readCSV` off-by-one，11 列畸形行 panic | 修正长度判断，并解析 `error` 列、剔除执行错误样本 |
| 低 | `waf_allow` 事件从未写入，与 SentinelWatch 契约不符 | 放行路径也落审计（`-log-allows`，默认开） |
| 低 | 429 被驱动器当成"放行"，开限流跑语料会虚增绕过数 | 429 记为执行错误，不进拦截率分母 |
| 低 | path/body/UA 里的 `+` 被当成空格 | `+` 只在 query 语义下解码 |
| 低 | 规则权重与阈值硬编码 | 阈值可用 `-semantic-threshold` 调整，便于做权重实验 |
| 低 | 无优雅关停，`ErrServerClosed` 也会 fatal | `signal.NotifyContext` + `Shutdown` |
