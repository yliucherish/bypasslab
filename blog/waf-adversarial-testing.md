# 我给自己的 WAF 做了四轮对抗测试：100% 拦截率是假的

> 全部数据来自我写的开源项目 BypassLab（Go，零第三方依赖），所有测试仅针对本地靶场与自建环境。
> 仓库：`github.com/yliucherish/bypasslab`
> 复现：`bash scripts/run_w4.sh`（四轮）、`bash scripts/run_holdout.sh`（冻结集）、`go run ./cmd/attack -crs`（CRS 基准）

## TL;DR

同一个 WAF，同一套驱动器，四轮对抗 + 两轮补丁：

| 轮次 | 语料 | 本轮做了什么 | 拦截率 | 误报率 |
|---|---|---|---|---|
| R1 | 108 条（84 攻击 + 24 良性） | —（v1.0 规则原样） | **79.8%**（67/84） | 0%（0/24） |
| R2 | 112 条 | 按 R1 暴露的缺口修补 | **100%**（84/84） | 0%（0/28） |
| R3 | 130 条（+18 条更难变形） | **规则一个字没改，只换语料** | **94.1%**（96/102） | 0%（0/28） |
| R3′ | 130 条 | 补 6 条归一化/规则 | **100%**（102/102） | 0%（0/28） |
| R4 | 124 条（**12 条全新构造**） | 不参考任何缺口清单，重新出题 | **97.9%**（94/96） | 0%（0/28） |
| R4′ | 124 条 | 补 2 条 | **100%**（96/96） | 0%（0/28） |

看着像收敛了。但上面所有 100% 都有一句话没说：**语料参与了调参**。

所以我又留了两把不参与调参的尺子：

| 语料 | 条数 | 拦截率 | 性质 |
|---|---|---|---|
| 自造训练集（R4） | 124 | 100% | 参与过调参，**不代表泛化能力** |
| **冻结 holdout** | **19** | **63.2%**（12/19） | 从未做过针对性修复 |
| **OWASP CRS 官方回归集** | **59** | **39.0%**（23/59） | 第三方标准，一次都没为它改过规则 |

**100% → 63.2% → 39.0%**。这三个数字放在一起，才是这个项目真正的结论。

如果你只想发一条朋友圈，你会发 R2 的 100%。但 63.2% 才是真相。

---

## 一、为什么要自己打自己

起因很简单：我用 Python 写过漏洞扫描器（VulnHunter），也写过主机日志检测引擎（SentinelWatch），
但一直答不上来一个问题——**规则加到什么程度算够？**

写了 16 条正则就觉得差不多了，可"差不多"是什么标准？没人告诉我。

于是我写了个反向代理式 WAF：Layer 1 是 16 条正则（覆盖 SQLi / XSS / RCE / 路径遍历 / 反序列化 / SSRF / 扫描器指纹），
Layer 2 是 16 项语义特征加权评分（shell 元字符、命令名、`../` 序列、Java 反序列化魔数、`@type`、内网 IP 等，权重 1–4），
再加九步归一化管道、JSONL 审计、限流。

然后写了个驱动器批量打它。

好处是：**WAF 和攻击方都是我自己的代码**，每一次绕过都能追到具体哪条规则、被哪种变形绕过——
用别人的工具打自己的系统，你只能看到"没过"，看不到"为什么没过"。

## 二、R1：79.8%，归一化把我的输入改坏了

第一轮语料 108 条（84 攻击 + 24 良性对照），跑完 **79.8%，误报 0%**。

分类看，短板非常清楚：

| 类别 | 拦截率 |
|---|---|
| 路径遍历 / 扫描器指纹 | 100% |
| SQL 注入 | 86% |
| 命令注入 | 83% |
| 反序列化 / XSS | 80% |
| **SSRF** | **12%** |

SSRF 几乎不设防。一开始我以为只是规则没写，加了一条正则——**还是 0 命中**。

回头 dump 归一化后的字符串，才发现真因：

```
输入:     url=http%3A%2F%2F127.0.0.1%3A6379%2F
归一化后: url=http:/127.0.0.1:6379/       ← http:// 被折成了 http:/
```

我的归一化里有一步"折叠重复斜杠"（为了防 `..//..//` 这类遍历变形），
它把 URL 协议分隔符 `://` 也当成重复斜杠折掉了。**规则写得再对也没用，输入已经被自己的清洗逻辑改坏了。**

这条教训比加十条规则都值：**改了归一化，必须亲眼看一遍它的输出。**
这句话我后来写进了项目的 SPEC 里。

## 三、R2：100%，但我不信

按 R1 暴露的清单补了四类：SSRF 专用规则（危险协议 + 内网/元数据地址组合）、
命令拼接补单竖线 `|` 与解释器命令名、引号包裹的恒真式单独计分、归一化补 Log4Shell 的 `${lower:x}` 混淆展开。

重跑：**100%（84/84），误报仍 0%**。

数字很漂亮，但我心里清楚：**这 84 条我刚才逐条看过，规则就是照着它们的缺口写的。**
这叫拟合，不叫防护。

## 四、R3：只换语料，规则不动，掉到 94.1%

我加了 18 条之前没写过的变形，规则一个字没改：

- SSRF：十进制 `2130706433`、十六进制 `0x7f000001`、IPv6 映射 `[::ffff:127.0.0.1]`、短写 `127.1`
- 路径遍历：`..%c0%af`（超长 UTF-8 斜杠）
- XSS：`\u003cscript`（Unicode 转义）
- SQL 注入：`/*!50000union*/`（MySQL 版本注释）、`un/**/ion se/**/lect`（关键字中间插注释）、`and (1)=(1)`（括号包裹恒真式）
- 反序列化：`${${env:FOO:-j}ndi:...}`（JNDI 用 env 默认值拼关键字）

结果：**94.1%（96/102）**，6 条被放行。

这 6 条归成两类，特别有代表性：

| 类型 | 根因 |
|---|---|
| 归一化层缺一步 | 只认点分十进制 IP，不认数值化/十六进制/IPv6 映射；不解超长编码与 Unicode 转义 |
| 规则层缺一步 | 注释剥离后没还原关键字；恒真式不认括号；JNDI 只展开了 lower/upper，没展开 env 默认值 |

**共性：能挡住"已知写法"，挡不住"同一语义的另一种写法"。**

补完这 6 条，又回到 100%。但这时候我已经不敢信了。

## 五、R4：不参考缺口清单，重新出题

R3′ 之后我做了一件当时觉得很多余的事：**不看自己列的缺口清单**，只问一个问题——
"同一个语义，还能怎么换写法？"然后构造了 12 条全新样本。

结果 **97.9%（94/96）**，又漏了 2 条：

| 样本 | 根因 |
|---|---|
| `/*!50000un*/ion select` | 版本注释展开时前后补了空格，把 `un` 与 `ion` 断开 |
| `http://017700000001:6379/` | 单段 IP 归一只认十进制与 `0x`，漏了前导 0 的八进制写法 |

这两条都不在 R3 的缺口清单里——**它们是被"重新出题"逼出来的，不是被"照着清单改"改出来的。**

补完又回到 100%（96/96）。

**这张表最值得讲的一点是：每次修到 100%，就再出一批新题，然后又掉下来。**
所以表里唯一能代表泛化能力的数字是 R1 的 79.8%——它是在"没有针对任何缺口做过修复"的状态下测出来的。

## 六、holdout：一个不会说谎的数字，63.2%

上面所有 100% 都有一个共同前提：**语料参与了调参**。修完 R1 修 R2、修完 R3 修 R4，
每一批最终都会被修到 100%。它们是训练集，不是测试集。

所以我单独留了一批**冻结语料**（`internal/payloads/holdout.go`，19 条），并给自己定了三条硬纪律：

1. **不进任何主流程**：只由 `scripts/run_holdout.sh` 单独跑，CI 与 `run_w2/run_w4` 都不含它；
2. **只报总数，不报明细**：输出里连哪几条漏了都不打印——不知道是哪条，就没法针对性修；
3. 文件头写死：**任何情况下不得据此修改规则**。规则改动后重跑，数字下降是正常的。

结果：

```
holdout 19 条 → 12 条拦截 → 63.2%
```

**这 37 个百分点的差距，才是这个项目真正的结论**：规则型 WAF 对"同一语义的另一种写法"的真实拦截率
在六成上下，不是 100%。任何只报 100% 的评测，几乎一定是在测试集上调过参。

为什么这个数字不修？因为**一修它就变成训练集了**。它的价值恰恰在于一直难看。
如果哪天规则真的泛化了，它会自己涨上去——那才叫进步。

## 七、CRS 39.0%：第三方给的分数

holdout 虽然冻结，但它仍是我自己造的。真正的第三方基准是 **OWASP CRS 官方回归测试集**
（`github.com/coreruleset/coreruleset` 的 `tests/regression/` 目录）。

我把其中四个规则文件（942100 SQLi / 941100 XSS / 930100 LFI / 932130 RCE）逐条转写成我们的语料格式，跑了一次 `-crs`：

| 语料 | 条数 | 拦截率 | 误报 |
|---|---|---|---|
| 自造训练集（R4） | 124 | 100% | 0% |
| 冻结 holdout | 19 | 63.2% | 0% |
| **CRS 官方测试集** | **59** | **39.0%（23/59）** | 1/8* |

\* 那 1 条"误报"是口径差异：CRS 的 libinjection 不检查 Referer 头，我们检查——
payload 放在 Referer 里 CRS 放行、我们拦截。这不是缺陷，是我们比 CRS 激进的代价（已计入，不掩饰）。

CRS 暴露的缺口，每一类都不是"加一条正则"能解决的：

| 缺口类别 | 样本数 | 为什么难 |
|---|---|---|
| bracket globbing（`/etc/pa[s]wd`） | ~10 | 需要 shell 通配符展开语义，正则难覆盖所有组合 |
| IIS `%uXXXX` best-fit 编码 | 3 | IIS 专属解析行为，要先识别再折叠 |
| XML 载体（属性注入） | 3 | 需要 XML 解析器，否则看不到属性值 |
| 自定义标签（`<x:script>`） | 2 | 需要理解命名空间 |
| CRS 自家特征串 | 2 | CRS 针对自己规则设计的特征，对别的 WAF 无意义 |

**这 61% 的差距，就是工业界规则的护城河。** CRS 社区用十几年积累了上千条规则才覆盖这些场景，
我一个人写了两个月的东西能做到 39%，反而是个合理的结果——如果我也是 100%，那才叫见鬼。

## 八、三个方法论收获

**1. 拦截率必须和语料绑定陈述**

"我的 WAF 拦截率 94.1%，语料是 130 条自建样本，其中 18 条为未经调优的变形"——这句话有信息量。
"拦截率 100%"——没有信息量，因为你不知道它是不是只测了 5 条。

**2. 误报是硬约束，不是附带指标**

我全程保持 28 条良性样本 **0 误报**（含"搜索词里出现 select"、"含单引号的文本"、"正常外链回调"）。
为什么要守？因为**降阈值能立刻把拦截率拉到 100%，代价是业务被打挂**。
只报拦截率不报误报率的 WAF 评测，等于只报收入不报成本。

**3. 判定口径会骗你**

最初我用"HTTP 403"判断拦截。问题是我测的时候上游服务自己也会返回 403（鉴权失败），
这会被算成 WAF 拦住了——拦截率虚高十几个百分点。

改成双条件后才准：**403 + 响应头 `X-BypassLab-Blocked` 存在**。
我还专门写了个测试：起一个固定返回 403 的上游，验证它不会被误判。这个测试现在还在仓库里。

## 九、把实验台做成能用的东西

对抗做完，顺手补了三件让它"像产品"的事，因为面试官常问"这东西能上生产吗"：

**1. 规则外置 + 热加载**
规则挪到 JSON 文件，mtime 轮询监听，配置改动 **2 秒生效**。
关键是"坏配置不裸奔"：新规则集任何一条校验不过，**整份拒绝**，继续用旧规则，而不是加载一半。

**2. 流式 body 检测**
原来超过 2MiB 直接 413——这是个笑话，攻击者只要发 3MiB 就能整体绕过检测。
改成 8KB 重叠窗口的分块扫描：大文件上传正常通过，藏在第 1.9MiB 的 payload 照样被拦，跨块的载荷也能拼回来。

**3. 性能量化**

| 环节 | 单核耗时 |
|---|---|
| 归一化（九步管道） | 6.0 µs |
| 攻击载荷（命中即返回） | 11.1 µs |
| 良性请求（走完全部 32 项检测） | 57.2 µs |
| **端到端**（限流 + 检测 + 审计 + 转发） | **174 µs ≈ 5.7k QPS** |

瓶颈很明确：良性请求必须走完 16 条正则 × 4 个部位 + 16 项语义特征，而归一化还要对每个字段做多轮解码。
5.7k QPS 保护一个小站够用；再往下是追 nginx 的尾灯，不如把时间花在规则上。

配套 58 项自动化测试 + 4 组基准，CI 里跑 `-race` 检测数据竞争。

## 十、局限（诚实版）

- **语料是我一个人写的**，覆盖面受我的认知限制。真实攻击面比我列的广得多——CRS 的 39% 就是证据。
- **它是实验台，不是能上生产的东西**：单机内存态限流、没有集群共享状态、没有管理后台、没有规则运营流程。
- **39.0% 和 63.2% 都只对各自那套语料成立**，不要外推成"这个 WAF 的防护能力是 39%"。
- 我没做过真实 HW 攻防，所有结论都来自本地靶场。

## 十一、下一步

短期想把 CRS 的 39% 往上推——bracket globbing 和 XML 属性注入是两块能啃的骨头，
但不是"加正则"，而是要引入 glob 展开和 XML 解析，属于架构改动。

长期我更好奇另一件事：**能不能让规则自己发现自己的盲区**。
比如把 holdout 的漏报样本喂给一个变异器，让它生成"同一语义的 N 种写法"，再批量测——
这比人肉想变形快得多，也接近"智能化漏洞挖掘"真正该有的样子。

补完之后大概又会回到接近 100%，然后我又要造一批新变形把它打下来。
**这个循环本身，就是"对抗"两个字的含义。**
